<objective>
Expose the cancellation mechanism proven in 04-01 across the backend↔tts_service HTTP boundary: a `POST /cancel` endpoint on `tts_service/server.py` that calls `request_cancel()`, and a best-effort `cancel()` function in `backend/app/tts_client.py` that POSTs to it. Also make `server.py`'s `/synthesize` handler treat `GenerationCancelled` as a deliberate stop, not a 500. This is the thin HTTP surface both ends of the new cancel call need; the backend orchestration that actually calls `cancel()` and manages tasks/locks is plan 04-03.

Purpose: Give the backend a single call it can make to shorten the in-flight GPU synth (per ARCHITECTURE.md, this alone makes the existing blocking `httpx.post` return promptly — no client rewrite).
Output: `POST /cancel` (tts_service), `GenerationCancelled` handling in `/synthesize`, `tts_client.cancel()` (backend).
</objective>
