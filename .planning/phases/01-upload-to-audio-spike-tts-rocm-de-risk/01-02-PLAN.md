<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backend container → TTS `/synthesize` (internal pod network) | Chunk text + speaker cross an internal HTTP boundary |
| Host → GPU devices (`/dev/kfd`, `/dev/dri`) passed into the TTS container | Kernel device access granted to a container |
| Container build → PyPI / rocm wheel index | Third-party package installs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | `/synthesize` speaker/text input | mitigate | qwen-tts `get_supported_speakers()` validation raises `ValueError` -> return `400`; reject empty text; do not re-implement an allowlist (Task 2) |
| T-02-02 | Denial of Service | `/synthesize` unbounded text length | mitigate | Cap accepted text length in the endpoint; backend pre-chunks to ~800 chars (Task 2) |
| T-02-03 | Elevation of Privilege / Info Disclosure | GPU device passthrough into container | accept | Single trusted user (Tailscale boundary project-wide); rootless Podman + `--group-add keep-groups`; SELinux left Enforcing with already-correct device labels (`hsa_device_t`/`dri_device_t`); TTS port not published externally in the deployed pod (Plan 03) |
| T-02-SC | Tampering | pip installs (`qwen-tts`, `transformers`, `accelerate`, base image) | accept | All packages `[VERIFIED]`/`OK` in RESEARCH.md Package Legitimacy Audit (slopcheck clean); exact-pinned; official `rocm/pytorch` base tag verified to exist. No `[ASSUMED]`/`[SUS]` packages -> no blocking legitimacy checkpoint required |
</threat_model>
