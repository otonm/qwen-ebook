<task type="auto">
  <name>Task 1: Distinguish a permanent 404 from a transient EventSource drop</name>
  <files>frontend/src/hooks/useAnalysisStream.ts</files>
  <action>
In the source.addEventListener("error", ...) handler: today, when
messageEvent.data is empty it unconditionally returns (treat as transient and
let EventSource reconnect). That is correct for a real network blip but wrong
for a project that no longer exists — the 404 is permanent and the reconnect
loops forever.

Fix: on a no-data error event, do a single confirmation fetch of the project to
tell the two cases apart. Reuse the existing getProject(projectId) client
helper — it throws for a non-ok response (parseJsonOrThrow). Logic:
  - Guard against repeated probing: use a ref flag (e.g. probingRef) so at most
    one confirmation fetch is in flight per error burst — do not fire getProject
    on every reconnect attempt.
  - Call getProject(projectId). If it RESOLVES, the project still exists (likely
    genuinely still analyzing) — treat the error as transient: reset the probe
    flag and return, letting EventSource keep reconnecting (current behavior).
  - If it REJECTS (404 / project gone), this is permanent: close the source and
    setState status='error' with a clear detail such as "This project no longer
    exists." App.tsx's ErrorScreen then offers "Upload another file" whose
    onRetry clears the stored projectId and returns to the list — the recovery
    path already exists, the hook just has to reach 'error'.

Keep the existing has-data branch (server-sent SSE 'error' event) unchanged.
Reset probingRef in the effect's setState(initialState()) reset block / cleanup
so a new projectId subscription starts fresh.

Do not add a test framework (none exists in frontend/). Verify via the type/
build check below plus the human-verify checkpoint.
Run `cd frontend && npm run lint` if a lint script exists and fix warnings.
  </action>
  <verify>
    <automated>cd frontend && npm run build</automated>
  </verify>
  <done>A no-data error triggers one confirmation fetch; a resolved fetch keeps the transient-reconnect behavior, a rejected (404) fetch drives status='error' so App.tsx can recover to the project list. `npm run build` (tsc + vite) passes.</done>
</task>
