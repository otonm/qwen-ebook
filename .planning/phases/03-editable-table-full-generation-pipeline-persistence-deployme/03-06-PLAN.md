  <name>Task 1: Add a persistent data volume for the backend's writable state</name>
  <files>deploy/qwen-ebook-backend.container, backend/Containerfile.backend, deploy/run-local.sh, backend/tests/test_config.py</files>
  <action>
The backend's SQLite DB (config.py DATABASE_URL default sqlite:///.../backend/projects.db),
uploads (UPLOAD_DIR -> /backend/uploads), output (OUTPUT_DIR -> /backend/output)
and previews (PREVIEW_DIR derives to OUTPUT_DIR/previews) all live inside the
container's writable overlay today. The tts unit already persists its HF cache
via a named volume; the backend has no equivalent. Give it one.

CRITICAL constraint: the frontend bundle is COPY'd into /backend/static at
build time (Containerfile.backend line ~52). Do NOT mount the volume at
/backend — that would shadow the baked-in static assets and 404 the whole UI.
Mount persistent state at a SEPARATE path (/data) and point config there via
env vars, leaving /backend/static image-baked and untouched.

Backend Quadlet unit (deploy/qwen-ebook-backend.container), add under [Container]:
  - Volume=qwen-ebook-data:/data
  - Environment=DATABASE_URL=sqlite:////data/projects.db   (four slashes = absolute /data path)
  - Environment=UPLOAD_DIR=/data/uploads
  - Environment=OUTPUT_DIR=/data/output
  (PREVIEW_DIR auto-derives to /data/output/previews via config.py — no extra
  env needed.)

Containerfile.backend: the container runs as appuser (uid 1000). A fresh
Podman named volume inherits the ownership/permissions of the image's mount-
point directory via copy-up, so pre-create /data owned by appuser BEFORE the
`USER appuser` line. Extend the existing mkdir/chown RUN step to also create
/data/uploads /data/output and chown -R appuser:appuser /data (alongside the
existing /app /backend chown).

deploy/run-local.sh: mirror the same persistence on the manual bring-up path so
dev and prod don't silently diverge (the same data-loss bug otherwise lives on
in run-local.sh). On the backend `podman run` invocation add:
  -v "${DATA_VOLUME:-qwen-ebook-data}:/data"
  -e DATABASE_URL=sqlite:////data/projects.db
  -e UPLOAD_DIR=/data/uploads
  -e OUTPUT_DIR=/data/output
Add a DATA_VOLUME variable near HF_CACHE_VOLUME with the same default.

test_config.py: add a test that sets DATABASE_URL/UPLOAD_DIR/OUTPUT_DIR env
vars to /data paths, calls load_settings(), and asserts DATABASE_URL,
UPLOAD_DIR, OUTPUT_DIR resolve to those values and PREVIEW_DIR derives to
/data/output/previews — proving the env overrides the unit file will set are
actually honored. Follow test_config.py's existing env-override test pattern.

Run `cd backend && uv run ruff check .` and fix any warnings.

<task type="auto">
  <name>Task 2: Make the units restart-resilient and document the correct procedure</name>
  <files>deploy/qwen-ebook.pod, deploy/qwen-ebook-backend.container, deploy/qwen-ebook-tts.container, deploy/README.md</files>
  <action>
Root cause (03-UAT.md test 1): the pod's default exit policy is `stop`, so once
both member containers stop (a `systemctl restart` stops them), the pod's infra
container exits and the pod service goes inactive; systemd's restart job for the
members then fails with "Bound to unit qwen-ebook-pod.service, but unit isn't
active" / "Dependency failed", and nothing comes back up.

Config change (deploy/qwen-ebook.pod): keep the pod alive across a member-
container restart by setting the infra exit policy to continue. In the [Pod]
section add:
  PodmanArgs=--exit-policy=continue
This keeps the pod (and its published loopback port) up when a member container
is restarted, so the member can be restarted individually without tearing the
whole pod down. Add a header comment explaining why (and that PublishPort stays
loopback-only — never change that per DEPL-02/T-03-13).

Member units (deploy/qwen-ebook-backend.container, deploy/qwen-ebook-tts.container):
add a [Service] section with Restart=on-failure so a crashed member restarts
itself rather than staying down.

IMPORTANT — VM-version caveat: the unit headers already warn that Quadlet's key
set shifted across Podman 4.4-5.x. Whether `PodmanArgs=--exit-policy=continue`
is honored must be confirmed on the actual VM (Task 3). If it is NOT honored on
this host's Podman, the documented fallback is the correct manual restart order
the user already found works. Capture BOTH in the README so the deployment is
recoverable either way.

deploy/README.md — rewrite the "Tear down / restart" section (and add a
"Persistence" note) to state:
  - The backend's writable state (DB/uploads/output/previews) now lives on the
    `qwen-ebook-data` named volume and survives restarts/reboots; the image is
    otherwise ephemeral.
  - Preferred restart: `sudo systemctl restart qwen-ebook-pod.service` (brings
    the pod + members back together), OR restart a single member now that the
    pod stays up via --exit-policy=continue.
  - Documented fallback recovery order if the pod is ever fully down:
    `systemctl start qwen-ebook-pod.service` then `qwen-ebook-tts.service`
    then `qwen-ebook-backend.service`.
  - Note the `--exit-policy=continue` behavior must be confirmed on the VM's
    Podman version (link to the post-deploy verification).

Do not weaken the loopback-only PublishPort or add any public exposure.
  </action>
